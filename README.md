# Fake Job Posting & Recruitment Scam Detection

A small Machine Learning mini-project (ML-2 assignment) that predicts whether a job
advertisement looks **genuine** or **potentially fraudulent**. The model is an
Artificial Neural Network built with **scikit-learn's `MLPClassifier`** — no PyTorch,
no TensorFlow, no transformers.

All numbers in this README come from an actual run of `python train.py` on the
dataset in `dataset/` (random_state = 42, so the run is reproducible).

## 4. Selected features (12 columns → 64 numeric inputs)

Only structured / easy-to-explain columns are used. Raw text is **not** vectorized
(no TF-IDF, no word embeddings) — we only use the **length** of the texts.

| # | Column | Type | Why it is useful |
|---|---|---|---|
| 1 | `employment_type` | categorical | Fake posts often use odd types (Part-time, Other) |
| 2 | `required_experience` | categorical | Fraudulent posts often say "Not Applicable" |
| 3 | `required_education` | categorical | Fraudulent posts often leave it "Unspecified" |
| 4 | `industry` | categorical | Many fake posts have no industry at all |
| 5 | `function` | categorical | Same as above |
| 6 | `telecommuting` | 0/1 | Work-from-home is common in scams |
| 7 | `has_company_logo` | 0/1 | Only 33 % of fake posts have a logo vs 82 % of real ones |
| 8 | `has_questions` | 0/1 | Real employers more often add screening questions |
| 9 | `has_salary_range` | 0/1 (new) | 1 if the posting shows a salary range |
| 10 | `description_length` | number (new) | Number of words in `description` |
| 11 | `requirements_length` | number (new) | Number of words in `requirements` |
| 12 | `company_profile_length` | number (new) | Number of words in `company_profile` (fraudulent posts average ~32 words vs ~96 for real ones) |

Columns such as `job_id`, `title`, `location`, `department` and `benefits` are dropped
to keep the project simple.

After One-Hot Encoding (`min_frequency=0.01`) the 12 columns become **64 numeric
inputs** for the network.

## 5. Preprocessing (all inside a scikit-learn `Pipeline`)

1. **Duplicates** – `drop_duplicates()` (the current dataset has none, kept as a safety step).
2. **Text lengths** – word counts computed for `description`, `requirements`, `company_profile`.
3. **Missing values**
   - categorical columns → filled with the literal string `"missing"`
   - numeric columns → filled with the **median**
4. **Encoding** – `OneHotEncoder(handle_unknown="ignore", min_frequency=0.01)`
   Categories appearing in less than 1 % of the **training** rows are grouped into one
   "infrequent" column; a category the user types that the model has never seen is ignored.
5. **Scaling** – `StandardScaler` on the numeric block (mean 0, std 1).
6. **Split** – `train_test_split(test_size=0.2, stratify=y, random_state=42)`
   → 14,304 train rows / 3,576 test rows, and the 4.84 % fraud ratio is kept in both.

**No data leakage:** the imputer, encoder and scaler are *not* fitted on the whole
dataset. They are steps of a `Pipeline`, and `pipeline.fit()` is called only on the
training rows. The test rows are only ever passed to `predict()`.

## 6. Handling the class imbalance (why and how)

With 4.84 % fraudulent postings, a lazy model that always answers "genuine" would be
95 % accurate and completely useless. `MLPClassifier` has no `class_weight`
parameter, so we use **random oversampling of the training set only**:

- 693 fraudulent training rows are sampled **with replacement** until they match the
  13,611 real rows → a balanced training set of **27,222 rows (50 % / 50 %)**.
- The **test set is never oversampled**. It keeps the real-world 4.84 % ratio, so the
  reported metrics are honest.

Effect: recall on fraud goes up a lot (the model stops ignoring the minority class).
The price is more false alarms, i.e. lower precision (~0.63). For this problem a false
alarm is acceptable ("verify carefully") while a missed scam is worse.

## 7. The ANN / MLP model

```text
Input  (64 features)
   ↓
Dense 64 neurons  – ReLU
   ↓
Dense 32 neurons  – ReLU
   ↓
Output 1 neuron   – sigmoid  (probability of fraudulent)
```

| Setting | Value |
|---|---|
| Library | `sklearn.neural_network.MLPClassifier` (ANN / Multilayer Perceptron) |
| Hidden layers | (64, 32) |
| Activation | `relu` |
| Output activation | `logistic` (sigmoid, default for binary) |
| Solver | `adam` |
| Learning rate | 0.001 |
| Max iterations | 100 |
| Random state | 42 |
| Epochs actually run | 100 (loss still improving, so no early stop) |
| Training time | ~32 s |

## 9. Experiments (one change at a time, `model/experiments.csv`)

| Experiment | Hidden layers | Act. | LR | Max iter | Iter. run | Accuracy | Precision | Recall | F1 |
|---|---|---|---|---|---|---|---|---|---|
| **Baseline (64-32, relu, lr=0.001)** | (64, 32) | relu | 0.001 | 100 | 100 | 0.9662 | 0.6275 | 0.7399 | **0.6790** |
| Learning rate = 0.0001 | (64, 32) | relu | 0.0001 | 100 | 100 | 0.9421 | 0.4448 | 0.7919 | 0.5696 |
| Learning rate = 0.01 | (64, 32) | relu | 0.01 | 100 | 100 | 0.9662 | 0.6354 | 0.7052 | 0.6685 |
| One hidden layer (32) | (32,) | relu | 0.001 | 100 | 100 | 0.9477 | 0.4748 | 0.7630 | 0.5854 |
| Three hidden layers (128-64-32) | (128, 64, 32) | relu | 0.001 | 100 | 100 | 0.9606 | 0.5727 | 0.7283 | 0.6412 |
| Fewer iterations (max_iter=20) | (64, 32) | relu | 0.001 | 20 | 20 | 0.9432 | 0.4500 | 0.7803 | 0.5708 |
| Fewer iterations (max_iter=50) | (64, 32) | relu | 0.001 | 50 | 50 | 0.9561 | 0.5320 | 0.7688 | 0.6288 |
| More iterations (max_iter=200) | (64, 32) | relu | 0.001 | 200 | 107 | 0.9614 | 0.5792 | 0.7399 | 0.6497 |
| Activation = tanh | (64, 32) | tanh | 0.001 | 100 | 100 | 0.9586 | 0.5541 | 0.7399 | 0.6337 |
| Activation = logistic | (64, 32) | logistic | 0.001 | 100 | 100 | 0.9595 | 0.5603 | 0.7514 | 0.6420 |

What the experiments show:

- **Learning rate** matters most. 0.0001 is too slow (underfits: F1 0.57). 0.01 trains
  fast and is almost as good as 0.001, but recall drops.
- **Deeper is not better** on this small feature set: three layers (0.641) and one layer
  (0.585) are both worse than the 2-layer baseline (0.679).
- **More iterations** (`max_iter=200`) did not help: scikit-learn stopped early at
  iteration 107 because the loss had stopped improving for 10 epochs, and F1 fell slightly
  to 0.650 (a little overfitting).
- **ReLU beats tanh and logistic** for this dataset.
- The baseline configuration (64-32, ReLU, lr = 0.001, 100 iterations) was the best, so
  it is the model saved in `model/fake_job_mlp.joblib`.

## 11. Streamlit demo — URL-first workflow

```bash
streamlit run app.py
```

### Default flow (automatic)

1. The page opens with a **job posting URL** box and a **🔎 Fetch & Analyze** button.
2. Paste a public job posting link, for example a company careers page
   (`https://job-boards.greenhouse.io/discord/jobs/8299493002`) or
   `https://www.python.org/jobs/8219/`.
3. The app downloads the page with `requests` and parses it with `BeautifulSoup`.
4. The extracted values are mapped onto the 12 model features and the **saved model**
   predicts immediately.
5. You see **✅ Likely genuine** / **⚠️ Potentially fraudulent**, the fraud probability,
   a table of the extracted details, the full extracted text (in an expander) and a list
   of details that could not be found on the page.

The manual form is **hidden** on this path — it is a fallback, not the main workflow.

### When a page cannot be read

If the page cannot be fetched (timeout, 404, login wall, CAPTCHA, bot block, JavaScript
only page) or if it contains no job description, the app:

- shows a friendly explanation of what went wrong,
- opens the **manual entry form automatically**,
- and runs the same model when the form is submitted.

### Partial extraction

If the description was extracted but, say, the industry or salary is missing, the app still
predicts. Missing values are left empty and the existing preprocessing pipeline
(`SimpleImputer` + `OneHotEncoder(handle_unknown="ignore")`) handles them exactly as it did
during training. The page lists which details were missing so you can see why.

### How extraction works (`job_extractor.py`)

| Step | What it does |
|---|---|
| URL check | only `http`/`https`, rejects private/local addresses, checks DNS |
| Fetch | `requests.get` with a 12 s timeout, 3 MB limit, honest User-Agent, no login/CAPTCHA bypassing |
| Strategy 1 | **schema.org JSON-LD** (`"@type": "JobPosting"`) — title, description, employmentType, hiringOrganization, qualifications, baseSalary. If a page has several JobPosting blocks, the one with the longest description wins; if there is no `<script type="application/ld+json">` tag, the page's JavaScript payload (Next.js/React streaming, `self.__next_f.push(...)`) is decoded and searched too — this is what makes micro1.ai and Ashby work |
| Strategy 2 | **HTML heuristics** — description containers (scored by text size *minus* navigation links), section headings ("Requirements", "Responsibilities", "About us"), `og:` meta tags, logo `<img>`, form radio buttons, salary regex; "Related jobs"-style blocks end the posting and runaway sections are trimmed |
| Validation | needs ≥ 40 words of description **and** job-body signals; job *listing* pages (many job links) and marketing homepages are rejected |
| Mapping | `FULL_TIME`→`Full-time`, `bachelor`→`Bachelor's Degree`, `senior`→`Mid-Senior level`, industry/function matched against the training categories, anything unknown → missing |
| Output | a dict with exactly the 12 feature columns used by `preprocessing.build_input_dataframe` |

## 12. Limitations (nice to mention in the viva)

- Only 12 coarse features: the model reads **word counts**, not the meaning of the text,
  so a well-written scam can still slip through.
- The dataset is from 2014–2015 and is dominated by US/English postings, so it does not
  generalize to all job markets.
- ~26 % of real fraudulent postings are missed (recall 0.74) and ~37 % of the flagged
  postings are false alarms (precision 0.63). Accuracy alone (0.97) hides this.
- Oversampling creates duplicate fraudulent rows, which makes the model more aggressive
  (higher recall, lower precision).
- The 0.5 probability threshold is a choice; lowering it catches more fraud, raising it
  gives fewer false alarms.
- URL extraction is **best effort**: Naukri, Indeed, Glassdoor, Foundit and Workday answer
  with HTTP 403/429 (bot protection) and Hirist renders the posting with JavaScript, so a
  plain `requests` fetch cannot read them. The project deliberately does **not** bypass
  logins, CAPTCHAs or paywalls — those cases show the reason and fall back to manual entry.
  `model/website_compatibility.csv` lists exactly which sites were tested and what
  happened, so nothing is over-claimed.
- Extraction gives the model *approximate* values (e.g. the "requirements" section depends
  on how the page is structured), and any field that is not found is simply treated as
  missing. This is why partial extractions still produce a valid prediction.

## 13. Quick viva answers

- **Why MLP and not a decision tree / logistic regression?** The assignment is about an
  ANN; the MLP can learn non-linear combinations of the 64 encoded features.
- **Why One-Hot Encoding?** Categories like `employment_type` have no order, so numbering
  them (0,1,2…) would create a false "bigger than" relation.
- **Why StandardScaler?** Word counts (0–1000) are much larger than 0/1 flags; scaling
  puts all features on a similar range so gradient descent (Adam) trains properly.
- **Why stratify?** To keep the same 4.84 % fraud ratio in the train and test split.
- **Why is accuracy misleading?** Always predicting "real" would already give 95 % accuracy.
- **Where is the input / hidden / output layer?** 64 input features → 64 → 32 hidden
  neurons → 1 sigmoid output.
- **How does the URL mode work?** `requests` downloads the public page, `BeautifulSoup`
  finds the posting (schema.org JSON-LD first, HTML heuristics second), the extracted
  values are mapped onto the same 12 features, and the already-trained model predicts.
  Nothing is retrained.
- **What if the page cannot be read?** The app says why (timeout, 404, login/bot block,
  no description found) and switches to manual entry. It never bypasses logins, CAPTCHAs
  or paywalls.
- **What if only some fields are found?** The extraction is still accepted: missing values
  are left empty and the pipeline's imputer/encoder treat them as missing, exactly as
  during training.
